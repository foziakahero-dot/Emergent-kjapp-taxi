# SNAR · trusselmodell

Verdier som trenger beskyttelse er identitet og dokumenter, posisjon i sanntid, turhistorikk, adgang til flåter, rett til å disponere utbetalinger og leverandørtilgang. Kunde og sjåfør bruker mobilnett. Admin og løyvehaver bruker nettleser. Begge når FastAPI via HTTPS eller Socket.IO. Backend tar autorisasjonsbeslutningen og kommuniserer videre med Atlas, betalings-, kart-, e-post-, identitets- og varslingstjenester. Eksterne systemer og klienter gir inndata ved hver av disse grensene.

| Grense og scenario | Krav og kontroll | Test eller gjenstående bevis |
| --- | --- | --- |
| Mobil → API. Feil identitet, gyldig token for feil rolle | Verifiser leverandørsignatur, utsteder og mottaker. Kontroller gjeldende rolle og sperring i databasen. OTP begrenses i tid og antall forsøk. | Lokale auth-/OTP-tester. Krever Google, Apple og SMS på aktuell fysisk kandidat. |
| Nettleser → Admin/Fleet. Gjenbruk av sesjon eller handling på vegne av bruker | Admin krever tofaktor. Sesjonsbevis, atomisk reservekode, kontroll av cookie-opprinnelse og ny autentisering på sensitive skriveruter. | Nye grense- og paneltester. Følg opp passnøkler med sikker registrering og gjenoppretting. |
| Kunde, sjåfør eller flåte → tur, dokument eller posisjon | Autoriser objektet og handlingen med eier, flåte, tildelt tur og fase. Delingslenker har utløp. Reduser presisjon og felter til det formålet trenger. | Rolle-/flåtetester, turtilstand, live socket med syntetiske kontoer. Rest: klientcache etter utlogging samt to separate fysiske enheter. |
| Klient → betalingssystem. Feil pris, mottaker, dobbelt oppgjør | Beregn pris på server, bind reservasjon til betalingsobjekt, miljø og kunde. Signer hendelser og utfør gjentatte leveranser idempotent. | Lokal Stripe-modell, virkelig SDK-signatur. Test avstemming, delvis capture, refusjon og kvittering hos Stripe i testmodus. |
| Internett → kant → Render. Kostnadsøkning eller manglende tilgjengelighet | Endepunktspesifikke grenser, tidsavbrudd, valgfri opprinnelsesverifisering og DDoS-beskyttelse ved kanten. | Testet off/observe/enforce lokalt. Verifiser faktisk DNS, sertifikat, alternative aliaser og godkjent klienttrafikk før håndheving. |
| Leverandør → backend. Uventet datastruktur eller stor kropp | Begrens inndata, verifiser før behandling og benytt sikker parser. | Webhookgrenser, syntetisk signatur og XML-endring. Kompletter med type-/størrelseskontroll for hver leverandør. |
| Repo, CI eller logger → utenforstående | Minste rettigheter, hemmeligheter i driftsmiljø, private sikkerhetsfunn, syntetiske fixtures. | Historikktreff trenger eierklassifisering. Vurder GitHub push protection, godkjente avhengigheter og gjennomgang av logger. |
| Vekstkampanje → økonomisk forpliktelse | Atomisk krav per verifisert kunde, definert kampanjegrense, beløp, idempotens og mottakeravstemming. | Endelig kampanjekandidat og samtidighetstest mangler. |
| Ansatt eller databehandler → personopplysninger | Formålsstyrt innsyn, revisjonsspor, tidsbegrenset tilgang og sletting. | Verifiser støtte-/driftsroller, dokumenthistorikk, leverandøravtaler og øvelse i innsyn/sletting. |

ASVS-områder omfatter autentisering, sesjoner, tillatelser, inndata, API, databeskyttelse og logger. API1/3/5 prioriterer objekt-, felt- og funksjonstilgang. API2 gjelder identitet, API4/6 ressursgrenser og forretningsflyter, API7/10 utgående kall og leverandørdata og API8/9 konfigurasjon og inventar. Utgående HTTP-tilgang og samtlige underleverandører krever egen verifisering. Modellen er et styringsgrunnlag, ingen sertifisering.
