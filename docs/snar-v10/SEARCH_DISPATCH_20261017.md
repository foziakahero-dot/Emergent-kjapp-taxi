# SNAR booking search and sequential dispatch

The customer's confirmed/authorized booking opens a full-screen `DriverSearchOverlay` with a large spinner, **Leter etter ledige sjåfører...**, elapsed seconds and **Avbryt søk**. It has no outside-dismiss or Android Back dismissal. The address-search panel remains separately minimizable; it is not the booking search. The query cache carries the just-created trip into the booking screen. Navigating within the app during an unassigned search returns to that screen.

Render persists a 60-second total deadline, starting after bank authorization. Only one driver at a time is offered the trip, nearest eligible driver first, for at most 30 seconds and never beyond the total deadline. Declining immediately advances to the next eligible untried driver. There is no broadcast fallback. Newly online eligible drivers are reconsidered while no offer exists. Pending-driver results hide expired/non-owned offers. Acceptance checks the offer owner/sequence, per-offer expiry and overall deadline atomically, preventing late acceptance or two winners. Offline, absent, away, on-break, busy, unapproved or unavailable cars are excluded.

At the deadline Render atomically cancels an unassigned search and releases its existing card reservation; it never captures it. The customer sees **Ingen sjåfører tilgjengelig akkurat, prøv igjen senere**. During lost network connectivity, the UI does not falsely claim a cancellation succeeded: it displays pending server confirmation. The spinner is removed by an accepted-driver state, confirmed cancellation or canonical no-driver timeout.

`POST /api/trips/{trip_id}/search/cancel` is customer-owned and idempotent. It only cancels an unassigned search. If acceptance wins the race it returns 409; the app fetches the canonical assigned trip rather than silently cancelling a fare-bearing trip. `GET /api/trips/{trip_id}` also reconciles search deadlines, and includes server time for a clock-skew-tolerant counter. The worker checks every 0.5 seconds; customer polling is one second, with app resume refresh. Persistent search survives app backgrounding and server restart.

Tests: bounded deadline and holds, retries/restart, per-offer progression, concurrent dispatch, acceptance vs timeout, customer-owned/idempotent cancellation, plus component tests for modal Back behavior, elapsed counter and single deadline callback. Real multi-device tests are still required before a production launch. Two full 30-second offers fit inside 60 seconds; quick declines can allow more offers within that same total limit.
