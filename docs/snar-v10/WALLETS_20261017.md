# SNAR Stripe wallets and return to app

## Implemented code

- Existing Stripe manual-capture reservation remains the payment authority. The backend authorizes the server-calculated ride price/accepted reservation limit before dispatch. Dispatch starts only after Stripe reports `requires_capture`. At the end of a trip the backend captures the actual final price, within the hold, once. Cancelling releases the hold; failed capture stays pending for reconciliation instead of showing a fake paid receipt. 3DS/insufficient-funds/cancel paths use the existing reservation recovery.
- Native Google Pay and Apple Pay use Stripe's PlatformPay SDK and official buttons. Wallet SetupIntents save a tokenized payment method with explicit consent for customer-booked rides; no fare is charged during setup. The server retrieves the SetupIntent and payment method to verify status, customer ownership and expected wallet type before storing token references and card metadata.
- Web uses Stripe.js Express Checkout Element in setup mode, directly inside the Customer app. Only Apple Pay/Google Pay are shown; Stripe controls browser/device eligibility. Confirmation calls Render for the SetupIntent and verifies the saved wallet through Render before selecting it for the next booking.
- Production support is coded but not automatically activated: key modes must match, environment must be production, and `NATIVE_PAYMENTS_LIVE_ENABLED=true` must be explicit. QA refuses live keys. Google/Apple/web wallets have separate activation flags.
- Native return from bank/Stripe uses the app's `kjapp://payment-methods` deep link and existing Stripe URL callback handler. Web card Checkout returns directly to `/payment-methods?setup=success&session_id=...` in the same approved app origin; cancellation returns `?setup=cancel`. Unknown return origins fail closed instead of silently sending the customer to a landing page. The app re-fetches verified payment methods after setup. This needs the updated app build.
- Refunds remain finance-authorized, audited and idempotent on Render. Failed/cancelled Stripe refund responses are rejected; reservation payments cannot be marked refunded through a manual fallback when Stripe is unavailable. Refund recovery from fleet funds after separate charge/transfer settlement is explicitly flagged for operations; it is not claimed to be automatic.

Full source: `backend/mobile_commerce.py`, `backend/ride_reservations.py`, `backend/server.py`; `frontend/src/lib/nativePayment.native.ts`, `nativeReservation.native.ts`, `nativeReservation.web.ts`; `frontend/src/components/WebWalletSetup.web.tsx`, `ApplePaySetupButton.native.tsx`, `GooglePaySetupButton.native.tsx`, `NativePaymentProvider.native.tsx`; `frontend/app/payment-methods.tsx`, `frontend/src/components/CustomerBookingView.tsx`, `frontend/app/(app)/home.tsx`.

## MANUAL: Stripe and Render

1. Use the existing Stripe account/sandbox; no replacement gateway/account has been created. Complete account verification and payment-method activation. Keep QA test keys/webhook secret isolated; configure production keys directly in Render. Never paste secret keys in chat or add them to Expo/Vercel public variables.
2. Verify the signed webhook endpoint `/api/stripe/webhook` in the appropriate mode and account. Events include `setup_intent.succeeded`, `payment_intent.amount_capturable_updated`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled` and the existing Checkout events. Server signature verification and reconciliation remain required; browser success is not proof of settlement.
3. Enable `NATIVE_PAYMENTS_ENABLED=true` with matching publishable/secret modes. For real payments additionally use `APP_ENV=production` and `NATIVE_PAYMENTS_LIVE_ENABLED=true` only after real device/sandbox tests and merchant approval. These live switches have not been enabled here.
4. QA flags: `QA_GOOGLE_PAY_ENABLED`, `QA_APPLE_PAY_ENABLED`, `QA_APPLE_PAY_MERCHANT_ID`, `QA_WEB_WALLETS_ENABLED`. Production uses the names without `QA_`. The native build's `EXPO_PUBLIC_APPLE_PAY_MERCHANT_ID` must match the server merchant ID.
5. Add the exact Customer web domain to `KJAPP_CHECKOUT_ALLOWED_ORIGINS` and existing CORS policy; set its intended default through `KJAPP_PUBLIC_WEB_ORIGIN`. Register the exact web domain in Stripe **Payment method domains**, separately in test and live mode, and ensure HTTPS. Customer web project/domain was not available among the connected Vercel projects, so this could not be completed here.
6. Review manual-capture authorization windows for the actual card networks and planned trip timing. Reservations can expire; recovery must never invent a paid state. Stripe funds availability cannot be inferred from frontend card validation.
7. Refunds use the original Stripe payment, not arbitrary customer-supplied amounts. Operations must monitor pending/failed refunds and the flagged separate-transfer fleet recovery. No actual charge or refund was executed during this implementation.

## MANUAL: Google Pay Console / Android

- Google Pay production access must be approved for the actual Android package `no.kjapp.app`, using the Gateway integration (Stripe), signed release app and requested review screenshots. Verify the app's identity/signing configuration, policies and business details.
- Test using Google's test environment first; the SDK derives `testEnv` from the server's Stripe mode. Production requires approval, live Stripe keys and a signed release with `testEnv=false`.
- The Expo Stripe plugin already enables Google Pay. Native wallets need an installed development/release build, not Expo Go.

## MANUAL: Apple Developer / iOS

- Register or select the real Apple Merchant ID, add Apple Pay capability to `no.nexorahub.kjapp.customer`, and regenerate provisioning when required.
- In Stripe's iOS certificate settings obtain the CSR, create the corresponding Apple Pay payment-processing certificate with Apple, and finish the Stripe setup. Do not substitute a locally generated CSR.
- Set the matching merchant ID in the EAS build environment and Render. Use a real supported Apple device with a Wallet card. Apple Pay native is for iOS; Android uses Google Pay. Web availability follows Stripe-supported device/browser combinations.
- App review/merchant approval and certificates are external steps; no claim is made that these accounts have been approved.

## Render dependency compatibility

Render also installs the existing `emergentintegrations 0.2.0` used by SNAR Assist. Its declared dependency requires `stripe>=13,<15`. Stripe Python therefore stays at the compatible 14.4.1 pin; the integration uses its supported `StripeClient.v1` API. Upgrading to Stripe 15 requires upgrading/replacing that helper package as a separate change. The focused payment tests were rerun with 14.4.1 before redeployment.
